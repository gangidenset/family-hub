# 07. セキュリティ設計

## 1. 脅威モデル

| 守るもの | 想定する攻撃者・リスク | 対策 |
|---|---|---|
| 家族の共有データ | 同じ Wi-Fi 上の第三者による盗聴・改ざん | WebRTC DTLS + アプリ層 AES-GCM、相互認証 |
| 〃 | QR コードの盗み見・撮影 | QR に長期秘密を載せない。DTLS フィンガープリント検証＋確認コード |
| 〃 | 別グループ・失効端末からの接続 | グループ鍵由来の HMAC 相互認証、鍵 epoch 更新 |
| 〃 | 細工されたバックアップ / 同期ファイル | サイズ上限・zod スキーマ検証・チェックサム・確認画面 |
| 〃 | XSS（悪意あるメモ本文を同期で送り込む等） | React の自動エスケープ、`dangerouslySetInnerHTML` 禁止、厳格な CSP |
| 〃 | 開発者・第三者サーバーへの漏えい | そもそも送信しない。CSP `connect-src 'self'`、STUN/TURN 不使用、解析 SDK なし |
| 〃 | 端末の盗難・紛失 | OS の画面ロックに依存（下記「限界」参照）。将来: アプリ内パスコード＋DB 暗号化 |
| アプリ本体 | 依存パッケージ経由のサプライチェーン攻撃 | 依存最小化、lockfile 固定、`npm audit`、ビルド成果物は外部 CDN を使わず自己完結 |

## 2. 設計上の判断（決定事項）

### S-1. 通信の暗号化（二重化）
- 経路: WebRTC は DTLS 1.2+ が必須で、暗号化なしの DataChannel は存在しない。
- アプリ層: 同期ペイロードをさらに AES-256-GCM で暗号化。**理由**: (1) 暗号化ファイル同期と同じ形式を使え、経路に依存しない E2E 暗号化になる (2) 万一の DTLS 実装の問題への多層防御。
- 鍵導出: グループ鍵（32 byte 乱数）から HKDF-SHA256 で用途別鍵（`auth`, `sync-enc`, `file-enc`）を導出し、用途間で鍵を共有しない。
- nonce: 96 bit 乱数（チャンク毎）。AAD にグループ ID・送信端末 ID・通し番号・プロトコルバージョンを含める。

### S-2. 認証
- ペアリング: QR（光学的な帯域外チャネル）で DTLS フィンガープリントを交換 → MITM 不可（Spike で改ざん時の接続失敗を確認）。さらに両画面の 6 桁確認コード（SAS）の一致をユーザーが確認してからグループ鍵を渡す。
- 同期: グループ鍵由来の認証鍵による HMAC チャレンジ・レスポンス。チャレンジに双方の DTLS フィンガープリントを含め、別接続への中継（リレー攻撃）を防ぐ。

### S-3. ローカルデータ
- IndexedDB はオリジン単位でブラウザが分離し、OS のサンドボックス・端末暗号化（iOS/Android の標準ストレージ暗号化）で保護される。
- **初期版ではアプリ独自の DB 暗号化は行わない**。理由: パスコードなしで暗号化しても鍵を同じ端末に置くことになり実効性が低い一方、毎回のパスコード入力は家族全員の使いやすさを大きく損なうため。将来オプションとして「アプリロック（パスコード/生体認証）＋鍵派生による DB 暗号化」をネイティブ版で検討。
- グループ鍵は `groupKeys` に保存。Web Crypto の non-extractable CryptoKey にすると暗号化バックアップができないため、raw で保存しアクセスは `src/sync/crypto` モジュールに限定する。
- `navigator.storage.persist()` で意図しない削除を防ぎ、定期的なバックアップを UI で促す。

### S-4. 外部データの取り込み（バックアップ・同期ファイル・QR）
1. サイズ上限（バックアップ 50 MB、QR 1 KB、同期チャンク 16 KB）を先に確認
2. JSON パース（失敗 → 拒否）
3. `format` / `formatVersion` 確認（未知・新しすぎる → 拒否）
4. チェックサム検証（破損 → 拒否）
5. zod スキーマで**全レコード**を厳格検証（型・文字列長上限・列挙値・ID 形式・日付形式）。プロトタイプ汚染対策として `__proto__` 等のキーを拒否
6. 参照整合性チェック（`listId` が存在するか等）。不整合は警告として確認画面に表示
7. 確認画面（グループ名・各データ件数・作成日時を表示）→ ユーザーが承認して初めて書き込み
8. 書き込みは単一トランザクション（途中失敗で中途半端な状態を残さない）。置換復元の直前には現在のデータを自動で退避

### S-5. 入力値バリデーション
- UI 入力・同期受信・復元のすべてで同じ zod スキーマを使用（ドメイン層に一元化）
- 文字列長上限: 名前 100 / タイトル 200 / メモ本文 20,000 / 数量 0〜9999 など
- 制御文字の除去（改行を許可するのはメモ本文・ノートのみ）

### S-6. XSS・Web 一般
- ユーザー入力は常にテキストとして描画（React のエスケープ）。HTML/Markdown のレンダリングは初期版では行わない。URL の自動リンク化を行う場合は `http(s):` のみ許可し `rel="noopener noreferrer"`
- CSP（meta または配信ヘッダー）:
  `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; connect-src 'self'; media-src 'self' blob:; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`
- `eval` / `new Function` / インラインスクリプト不使用
- 配信は HTTPS のみ（Service Worker・カメラ・Web Crypto の前提条件でもある）

### S-7. グループ間のデータ分離
- 全共有レコードに `groupId`。Repository 層の全クエリは「現在のグループ」を必須引数とし、複合インデックス `[groupId+...]` で検索
- 同期受信時、レコードの `groupId` が認証済みグループと一致しないものは拒否
- データ全削除はグループ単位で実行可能

### S-8. ログと個人情報
- 本番ビルドでは `console.log` を出さない（ESLint `no-console` + ビルド時除去）
- エラー記録はエラー種別コード・件数・時刻のみ。メモ本文・商品名・名前などの内容は記録しない
- クラッシュレポート・解析の外部送信はしない

## 3. 既知の限界（ユーザーに正直に伝える事項）

- 端末のロックが解除された状態で他人に端末を渡すと、アプリ内データは閲覧できる（初期版にアプリロックなし）。
- 失効させた端末に既にあるデータは削除できない。
- 「ファイルで同期」でメッセージアプリ等を使う場合、ファイルの存在・サイズ・送信日時は経路上のサービスから見える（中身は暗号化されている）。
- 暗号化なしの JSON バックアップファイルは平文。保管場所はユーザーの責任となるため、書き出し時に注意を表示し、パスフレーズ暗号化バックアップを推奨する。
