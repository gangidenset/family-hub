# Spike: サーバーなし WebRTC 接続 (QR コードによる手動シグナリング)

Phase 1 の技術検証用コードです。本番コードではありません（Phase 3 で `src/sync/` に正式実装します）。

## 検証したいこと

1. STUN / TURN / シグナリングサーバーを**一切使わず**に WebRTC データチャネルが張れるか
2. SDP（接続情報）を QR コード 1 枚に収まるサイズまで圧縮できるか
3. QR 画像 → 読み取り → 復元 の往復でデータが壊れないか
4. 中間者による接続情報の改ざん（DTLS フィンガープリント差し替え）で接続が**失敗する**か
5. 不正な入力（壊れた文字列・SDP インジェクション）を拒否できるか

## 仕組み

- `sdp-codec.js` — データチャネル用 SDP から接続に必要な最小情報（ICE ufrag/pwd、DTLS フィンガープリント、setup ロール、host 候補）だけを抜き出してバイナリ化 → base64url。受信側で定型 SDP を再構築します。
- `page.html` — ブラウザ側。`iceServers: []` の RTCPeerConnection を使用。
- `run.mjs` — 2 つの**独立した Chromium プロセス**を別端末に見立て、Offer → QR 化 → QR デコード → 相手に入力 → Answer → QR 化 → デコード → 入力、で接続し、双方向メッセージを確認します。QR の読み取りはカメラの代わりに `qrcode` で生成した画素データを `jsQR` でデコードしています。

## 実行

```bash
cd spikes/webrtc-qr
npm install
npm test
```

## 結果 (2026-11-08, Chromium 1243 headless, Linux コンテナ)

生データ: [`results-2026-11-08.json`](./results-2026-11-08.json)

| シナリオ | 結果 | 接続までの時間 | Offer コード長 / QR バージョン | Answer コード長 / QR バージョン |
|---|---|---|---|---|
| 既定（mDNS 難読化された host 候補） | ✅ 接続・双方向通信成功 | 約 5.4 秒 | 196 文字 / v9 | 116 文字 / v7 |
| mDNS 難読化無効（生 IP の host 候補） | ✅ 接続・双方向通信成功 | 約 5.4 秒 | 180 文字 / v9 | 100 文字 / v6 |
| フィンガープリント改ざん（MITM 模擬） | ✅ 期待どおり**接続失敗**（ICE は通るが DTLS で拒否） | — | — | — |

- 元の SDP は約 560〜590 バイト → 圧縮後 100〜196 文字（Offer には招待情報のテスト用ダミー約 60 バイトを同梱）。QR v9（53×53 モジュール, 誤り訂正 M）以下に収まり、スマートフォンのカメラで十分読み取れるサイズです。
- 接続時間の大半は ICE 候補収集完了待ち（5 秒タイムアウト）です。本実装では「host 候補が 1 つ以上出たら打ち切る」ことで短縮可能です。
- 不正入力: 不正文字・途中切れ・SDP インジェクション（ufrag に改行を混入）をすべて拒否しました。

## この検証で**分からない**こと（実機検証が必須）

- Android Chrome ⇔ iPhone Safari 間での接続（ブラウザ実装差）
- 実際の Wi-Fi での mDNS 名前解決（ルーターがマルチキャストを遮断する場合や AP 分離の場合は失敗する）
- iOS のホーム画面 PWA（standalone）でのカメラ読み取り性能
- 同一マシン上のループバックではない実ネットワーク越しの所要時間

これらは Phase 3 / Phase 4 の実機検証項目として `docs/06-sync-design.md` に記載しています。
